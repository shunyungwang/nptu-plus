# Phase 1 可行性報告：Flutter 手機端串接 NPTU 校務系統

> 結論先行：**可行**。技術路徑已由 Phase 1 實測貫通（登入→Session→資料頁→正式登出全流程成功），主要風險是 Session 單一化與驗證碼，皆有明確對策。待 Phase 3 把 PostBack 資料頁與公告補完後即可進入開發。

## 1. 已實測證明的能力

| 能力 | 證據 |
|---|---|
| 純 HTTP（無瀏覽器）完成登入 | curl + 全欄位 POST → `.PaAuth` 核發成功 |
| Session 由 Client 維持 | 後續 GET 全部以 CookieJar 成功取頁 |
| 無需瀏覽器 JS 執行環境即可取得資料 | A0515S 全表格資料是一次 GET 內嵌回傳（伺服器端渲染） |
| 正式登出可程式化 | POST Main.aspx + ibtLogOut → Session 註銷（實測受保護頁失效） |
| 完整功能已知 | 101 個功能項全部解析完成（menu.json） |

## 2. 技術限制與風險（與對策）

| # | 風險 | 嚴重度 | 對策 |
|---|---|---|---|
| 1 | 驗證碼無法（也不該）繞過 | 中（體驗） | App 內顯示驗證碼圖由使用者輸入；支援語音驗證碼提高可及性 |
| 2 | 同帳號單一 Session；非正常退出鎖 5 分鐘 | 中 | App 只保有一組 Session；背景恢復用「驗證失效→重新登入」策略；提供「真的登出」按鈕與說明文案 |
| 3 | WebForms 動態 VIEWSTATE/EVENTVALIDATION | 低 | 每次操作前先 GET 頁、即時解析欄位再 POST；做成通用 WebFormsClient |
| 4 | 無 REST API，資料為 HTML 表格 | 中 | 建 `data/parsers/` 專門 HTML→Model 解析層（`html` 套件），UI 不碰解析 |
| 5 | Session 有效期未知（可能閒置過期） | 低 | 任何請求偵測為轉址殼頁（如 177 bytes 特徵）→ 判定登入過期，走重新登入流程 |
| 6 | 頁面變版（title 顯示「VS2022」，學校會更新） | 中 | 解析器以欄位 `name` 為準而非位置；強化錯誤訊息；重要解析加 fallback |
| 7 | F5 Cookie 每回應重發 | 低 | CookieJar 自動跟隨最新值 |
| 8 | 錯誤猜測相對路徑（../Message 實為 /Web/Message） | 低 | 統一使用絕對 `/Web/...` 路徑常數 |

## 3. 整合方式比較（Phase 2 議題，初步結論供參考）

| 方式 | 評估 |
|---|---|
| **A. App 直接 HTTP（Dio + CookieJar）** | ✅ 推薦。資料不出手機以外的第三方；已驗證可行；依賴最少 |
| B. 中介伺服器代登入 | ❌ 不建議：需把學生密碼傳到第三方機器，違反專案安全原則 |
| C. Apify 擷取 | ❌ 已依使用者指示不使用：資料會上第三方雲端、成本/延遲、登入憑證不該交雲端 |
| D. WebView 內嵌 | ❌ 違反專案目標（需原生 UI + 自己管 Session） |

Phase 2 需再確認細節：Session 心跳策略、PostBack 參數封裝、登入過期自動重登條件、`html` 解析套件相容性、以及（必須）徵求使用者同意後才嘗試長期貯存憑證。
